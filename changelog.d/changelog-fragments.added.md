- `changelog` and `cut-release` learn release-note fragments: a pull request adds `changelog.d/<slug>.<section>.md` (one of `added`/`changed`/`deprecated`/`removed`/`fixed`/`security`) instead of editing `[Unreleased]`, so parallel branches no longer collide on the same region of `CHANGELOG.md`. The `check` gate reads fragments as pending content — the version-must-exceed, breaking-bump, and release-candidate rules apply to the combination, with a fragment's feature signal read from its filename suffix — and the cut folds them into the released section (existing `###` groups keep their order and gain the matching bullets, new sections append in canonical order), deletes the fragment files from the release commit, and creates the section outright for a fragments-only tree. Direct entries and fragments coexist, so adoption is gradual; the `fragments` input moves the directory. This very note rides in as a fragment — the convention's first dogfood.
